# How

探索代码回答"X 是怎么工作的"，产出相当于资深工程师上手一个子系统所需的架构讲解——够搭起工作心智模型，不到逐行注释源码的程度。

读代码的工具：仓库在本机就用本机文件夹/云端工作区 clone；在 GitHub 上就用 `github_*` 工具读文件、历史、PR。复杂子系统可以 message_bot 并行分头探索，每个委托带明确的角度和返回格式。

## 1. 评估复杂度

范围模糊就先给出你的解读再探索，用户可以纠偏。

- **简单**（单模块、小工具、"函数 X 怎么工作"这类窄问题）：自己探索并讲解，一次完成，直接进第 4 步。
- **复杂**（跨多文件/服务的子系统、横切功能、整体架构）：进第 2 步。

拿不准就走简单路径。

## 2. 探索（仅复杂问题）

把问题拆成 2–4 个角度，各是子系统的一个独立切片。可以并行委托给多个 BOT（message_bot），每个 brief 写清：角度、要看的文件/模块范围、要带回什么（调用链、数据流、关键类型、边界）。也可以自己按角度顺序探索。

## 3. 综合（仅复杂问题）

汇总各角度的发现成一份讲解。互相矛盾的说法要指出来并给出你更信的判断及理由。

## 4. 呈现

输出结构（不适用的节直接略去）：

- **Overview**：这段代码在系统里的位置，一段话。
- **Key Concepts**：理解它必须先知道的类型/术语/约定。
- **How It Works**：主流程的调用链或数据流，配 `file:line` 引用。
- **Where Things Live**：主要文件/目录/包的归属地图。
- **Gotchas**：非显然的坑、隐藏不变量、看起来像 bug 的故意设计。

引用一律给真实 `file:line` 或符号名，不许凭印象造位置。
