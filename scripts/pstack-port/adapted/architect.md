# Architect

先画草图：类型、函数签名、类形状、模块边界，函数体写 `not implemented` + 伪代码。至少两个结构不同的候选，合成后照图施工。

## 阶段

1. Ground　2. Sketch　3. Agree（可选）　4. Implement　5. Scrap

## A：Ground 问题

对每块新代码要碰的系统建立真实心智模型：跑 **how** 技能拿到子系统架构讲解。只说出文件名不算 grounded。设计若要重定义归属或分层，再跑 **why** 把历史理由变成约束而非猜测。

仅当真是没有周边系统可接入的绿地才跳过本阶段。

## B：Sketch

- 先写调用方用法，再从用法反推类型草图。
- **至少两个结构不同的候选**——整体形状的差异，不是同一形状内的点修（principle-exhaust-the-design-space）。可以自己做两版，也可以 message_bot 让另一个 BOT（建议不同模型）独立出一版再比较。
- 每个候选按这张红旗表过筛：假设下一个贡献者是只看了几个文件、抄最近例子、走最短路径的 agent——选"从单个文件看正确的改法对整个仓库也正确"的设计。
- 比较接口深度：选把更多复杂度藏在更小公共面后面的设计。
- 写合成决策：选哪个为基础、嫁接落选者的哪部分、为什么。

## C：Agree（可选）

默认不等人，直接进入实现。只有调用方明确要求检查点（"先给我看看再实现"）才停下签字。

设计被推翻时，把反馈当 A 阶段证据，重新 ground 后回 B。

## D：照图实现

把 `not implemented` 换成真代码，伪代码换成真逻辑。草图是契约：实现中任何偏离都是要显式上报的信号，不是默默吸收的摩擦。函数需要草图没预料的参数时，先问是草图错了、需求漏了还是实现越界。

## E：图错了就撕

实现持续产生草图吸收不了的摩擦时，扔掉草图，别给错设计打补丁（principle-redesign-from-first-principles、principle-fix-root-causes）。信号是**模式**而非个案：

- 同一种 workaround 在不相干代码里反复出现
- 多个不相关边界情形都要特例分支
- 类型要靠 `any`/断言/实际必设的可选字段才能编译
- 草图说状态不共享，代码却在要锁
- 调用方必须知道抽象内部规则才用得对
- 两处以上同形状的 D 阶段偏离

撕图流程：对已建成部分重跑 **how** → 按今天的约束重设计 → 新草图先比旧的小（principle-subtract-before-you-add）→ 回 B。

## 产出

调用方用法先行 + 类型/签名草图 + 合成决策理由。小改动一份文件；大改动模块地图加类型定义。
