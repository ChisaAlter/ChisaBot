# Bug 修复（playbook）

**你拥有这个 bug。复现、定位、验证。** 实现可以自己做，也可以委托给另一个 BOT，但验证纪律不外包。

1. **先复现。** 在真实表面上跑出 bug（云端工作区跑代码/测试，或照用户给的确切步骤）。复现不出来就先解决复现，不许直接猜改。
2. **二分假设。** 列出候选根因，用运行时证据逐个排除：加日志、跑最小复现脚本、git bisect、`git log` 回归区间。每个被排除的假设写明排除它的证据。改的是根因不是症状（principle-fix-root-causes）；两个修复死在同一道闸就攻击前提本身（principle-attack-the-premise）。
3. **计划。** 修复跨函数边界就先跑 **architect** 出形状，再动手。
4. **实现。** 自己改或 message_bot 委托另一个 BOT，brief 写清：要改的文件、根因结论、成功标准（复现从红变绿）、不许动的范围。"也许有用"的防御性代码是未验证假设，不许顺手加。
5. **同一表面验证。** 在第 1 步复现 bug 的同一表面、同一步骤上确认消失；再跑邻近路径防回归（principle-prove-it-works）。换表面验证不算数。
6. **提交顺序。** 有测试设施就先入库一个会因该 bug 失败的回归测试/复现脚本（tdd 技能），再入库修复——git 历史要能看出"先红后绿"。

**回复**：根因（含排除掉的假设及证据）、改动内容、复现前→修复后的证据对照。每条标 measured / inferred / guess。
