# 新功能（playbook）

**你拥有设计。计划、评审、验证。** 实现可委托给别的 BOT，你保持主导。

1. 跑 **how** 覆盖受影响的子系统。
2. 跑 **architect** 做并行设计探索，产出草图 + 合成决策。
3. 写吞吐检查点，四项各一行，不适用就标 `n/a: <原因>`：
   - **先做阻塞步骤**：有依赖关系的先跑。
   - **独立工作流**：不相交的文件/服务/层可并行，共享写串行。
   - **共享可变状态**：默认拆目标隔离写（principle-separate-before-serializing），只有真不变量才串行。
   - **最小安全拆分**：单执行者最优时说明理由。
4. **实现。** 自己写或委托：brief 给确切范围——文件路径、具名数据形状与其组织方式（principle-model-the-domain：状态机优先于散落布尔、表/注册表优先于分支、类型化模型优先于重复的性状假设——在写逻辑前定）、成功标准。实现存在多种合法形状（错误处理、抽象层、测试结构）时，让多个 BOT 各出一版再择优嫁接，而不是直接收第一版——评审分离是目的，不许以"省事"跳过。注释纪律：代码要自解释，不写复述代码的注释。
5. **匹配表面验证。** 功能在 UI 就开到 UI 上验，在 API 就打真请求验；"不确定"或用错表面不算通过（principle-prove-it-works）。
6. **提交切分。** 按 principle-sequence-verifiable-units 切成小的有序提交，每个单元独立构建、验证、入库。
7. 设计有争议就在交付前跑 **pstack-adversarial-review** 工作流对抗一遍。
8. 开 PR / 评论 PR 走 `github_*` 工具；PR 正文按 technical-writing：一分钟能读完的简报，链接证据而不是糊表格。

代码强耦合的活儿（一个功能一条迁移）归一个 owner，检查点内联在它的范围里；parent 级并行只留给产出独立制品的切片（审计、跨子系统调查、对比实验）。阶段边界重写检查点。

**回复**：建了什么、选了什么及为什么、吞吐检查点、待决项。设计候选用对照表。
