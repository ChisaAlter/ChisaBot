# 测试与验证

ChisaBot 的测试分四层：**单元 / 集成测试 → 预览容器里的端到端 → 回归套件 → 生产只读检查**。改动越接近聊天和真实数据，越要往后面的层走。
生产安全规则见 [release.md](release.md) §4，部署流程见 [ops/deploy.md](ops/deploy.md)。

## 0. 实机测试（硬性定义，严禁一切旁路）

**「实机测试」只有一个含义：测试者把自己当成真实用户——在真实部署版本上，用真实安装的客户端（PC 客户端 / Android 应用 / 正式 Web 界面），从真实登录开始，走用户实际操作的完整链路测一遍。任何功能（feature / fix）要报「完成」，必须 100% 过这个测试，无一例外。**

- 必须覆盖**整条用户路径**，每一环都是真的：
  - 真实公网地址上的正式部署版本（不是预览容器、不是本地起的服务）；
  - 真实登录：在登录界面输入真实凭据完成认证。**数据库里 INSERT 会话、注入 `x-chisabot-local-caller` 之类的内部认证头、复用服务端造的 token，全都是绕过鉴权层的冒充，不算数**；
  - 真实客户端：已安装的 PC / Android 应用，或正式 Web 界面。自动化驱动真实浏览器操作可见 UI 可以，但不得注入跳过产品层的头或参数；
  - 完整链路：客户端 → 生产服务端 → 真实配置与凭据 → 真实模型网关 → 回答回到界面并**肉眼可见**。
- **严禁用旁路测试冒充实机测试**，以下都只能算「辅助证据」，永远不能当实机结论报，严禁变通报关：
  - 直连适配器 / ACP / 内部接口，手动塞参数（如手工注入 `contextWindow`）；
  - 跳过服务端任何一层（鉴权、目录解析、队列、路由）直接调下游；
  - 重放 / 伪造 HTTP 请求代替真实客户端操作；
  - 拦截、改写、本地应答客户端的任何一个请求；
  - 预览容器、假模型、mock——它们验证的是代码路径，不是用户路径；
  - 数据库直写制造测试状态（造会话、改配置、插消息）。
- **旁路测试最大的陷阱**：手工喂的参数恰好绕开真正的 bug 点，显示「通过」而用户路径依然失败。验证手段必须和用户的入口一致——用户从登录页登录、从输入框发消息，验证就得从登录页登录、从输入框发消息。
- 报告时必须写清**实际验证的是哪条路径**、版本号、以及观察到的真实行为；任何一环是旁路的，整项标「未实机验证」，不得含糊带过、不得拆开了说「大部分链路是真的」。
- 实机验证不过，任何「已完成」的结论都不成立。缺真实凭据就做不了实机测试——那就如实报「未实机验证（缺凭据）」，而不是找替代品。

## 1. 单元 / 集成 / 类型检查

| 命令 | 范围 |
|---|---|
| `bun run typecheck` | `app`、`server`的 `tsc --noEmit`；其他组件按各自脚本检查 |
| `bun test` / 各包 `tests/` | ChisaBot 功能的服务器测试在 `server/tests/<功能>*.test.ts`（记忆、保险箱、定时任务、确认、设备、云端 CC…） |
| `bun run test:app` | 网页DOM测试；沿既有runner隔离会替换全局模块的用例，**需要 `NODE_ENV=test`** |
| `pc/` 下 `npm test` | PC 客户端（含外壳指纹一致性：改了图标 / 安装器要先 `npm run fingerprint`） |
| `android/` Gradle 测试 | Android壳、登录与WebView桥接；先本地验证，CI作最终检查 |
| CI「ChisaBot checks」（`.github/workflows/chisabot.yml`） | 每个 PR 必须绿；`bun install --frozen-lockfile --omit=peer --linker hoisted`（和镜像一样） |
| `pc-shots.yml` | 改到 PC 窗口 UI 的 PR 在 Windows runner 上截图（Windows Server 2025、1024×768、无 GPU：**没有 DWM 圆角**，DPI 用 `--force-device-scale-factor` 模拟） |

比较方法：固定版本和环境，核对改动所影响的行为；已知基线失败单列，不能把必要验收的失败改写为通过。本地实际路径完成后才触发最终CI，已有有效证据不重复运行。

## 2. 预览容器约定（端到端）

需要写数据的端到端都在**预览容器**里跑，不在生产上（服务器上的搭建方法见 [ops/preview.md](ops/preview.md)）：

- 用**生产镜像（或分支构建的镜像）+ 生产数据库的副本**起一个独立容器，绑 `127.0.0.1` 上自己的端口；每个 worker / 功能用自己的端口和容器名。
- **出网封锁**（或只放行假模型 / 假服务），保证预览里的机器人不会真的发消息、真的调第三方。
- 模型用**假模型**（OpenAI 兼容的 mock，见 `tests/chat-scroll/mock-model.mjs`），需要真模型时用一次性机器人。
- 浏览器用 playwright-core（镜像里的 Chromium），宽 1280 亮色 + 窄 390 暗色是最低覆盖；涉及布局的再加 900 / 1440。
- 同一数据库和状态机只设一个验收所有者，避免并发用例互相改数据。可复用状态明确的隔离副本，不因旧SQL问题机械重建已验证环境（见§5）。
- 收尾时停止自有临时执行；恢复副本、回滚材料和用户正在使用的预览按所有者约定保留。确认无消费者且已获授权后再删除专用资源。
- 可交互原型（给所有者点的）也用同样的隔离沙箱：数据副本 + 出网封锁。

## 4. 生产检查（只读）

上线后：

1. `/api/version` 的提交号是你的；更新器 `request.sh status` 成功。
2. **管理员自检** `POST /api/admin/smoke`（或设置 → 系统更新 →「自检」）：随机两位数加法，模型回答非空即通过，不保存任何东西。
3. **生产快照**对比（上线前后）：线程数、机器人数、设备数、用户数、关键设置哈希、新表行数——除镜像 / 版本外一致。
4. **只读浏览器检查**：临时签发一个会话 → playwright 打开页面，**拦截所有非 GET 请求**（本地返回 204），有副作用的 GET（如第一次读收藏夹会写种子、
   `/api/computers/*`）也在本地伪造，WebSocket 本地关闭 → 断言页面 / 接口 → 删除会话。
5. 必须真写的生产 e2e（少数情况）：一次性机器人 + 临时会话，跑完用守卫脚本删除，并核对快照。

§0 的界限同样适用于本节：第 4、5 项用到了临时会话与请求拦截，属于**辅助证据**，不是实机测试；任何功能的完成判定仍以 §0 定义的完整用户路径为准。

## 5. 已知问题与不稳定测试

| 问题 | 现象 | 处理 |
|---|---|---|
| **Bun 1.3.14 SQL协议错位** | simple BEGIN的两次ReadyForQuery分批抵达时，命名prepare可能错配参数或JSON结果类型 | `createDatabase`采用现有unnamed extended模式，配套Drizzle JSON序列化与raw Date ISO绑定；原直连API SIGKILL恢复已通过。监督层继续淘汰损坏连接且不重放失败请求；证据见[实施记录](pipeline-runs/20261108-assistant-production.md) |
| `approvals-rules.test.tsx` / `approval-tools.test.tsx` | main 上 2 个失败（「等待点击并入浏览器活动」DOM 用例），不是新改动引起；有时表现为超时 | 对比 main 时视为基线；修复待办 |
| app 全量测试中的上游英文用例 | 按文件跑时约 45 个上游测试文件在 main 上就失败（英文界面时代的文案断言） | 基线，不在范围内 |
| 全量跑时测试相互污染 | 个别改名后的测试在全量里失败、单独跑通过 | 单独复跑确认 |
| chat-scroll 节点替换与结束跳动（CB-087） | 基线七项出现旧消息重挂；结束留白按墙上时间追赶，慢帧倒退 | 渲染前协调窗口、稳定平级 keyed children、每帧有界收白；原七项严格阈值不变，整合构建复测并留 DOM reference / 逐帧数据。reduced-motion 额外覆盖宽窄屏；对应组件测试独立进程避免 Motion 媒体偏好缓存污染 |
| 长对话历史晚到（CB-047） | 冷预览上第一次打开超长对话，历史约 20 秒后到 → 偶发滚动回归 | 预热后再跑 |

| 冷启动第一个浏览器上下文 | 只读检查里客户端可能发两次 connect，被拦截后对话显示为空 | 测试脚本的已知假象，不代表生产问题 |
