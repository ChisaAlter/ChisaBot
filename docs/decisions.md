# 产品决策与需求原则日志

项目所有者提出的长期规则和产品方向，整理成中性的产品原则，按主题分组，每条带日期（北京时间）。
它们约束**之后所有的工作**；单个功能「为什么这样实现」的技术决定见 [ADR](adr/README.md)，界面细则见 [DESIGN.md](../DESIGN.md)。

- 新规则：加在对应主题下，写日期和原话要点；规则被替换时不删，标「已被 X 取代」并写新规则。
- 引号里是所有者的原话（只保留与规则有关的部分）。

## 1. 产品方向

| 日期 | 原则 | 说明 |
|---|---|---|
| 2026-10-15 | **核心是在任何地方管理所有设备（包括本地电脑）** | 云端机器人能读、改、写本地文件和代码；本地电脑要有像本地 OpenClaw / Hermes 那样的「完全权限」，同时有权限控制、沙箱和 agent 选择（「做」本地 agent 运行时）。→ ADR-0003 / 0009 / 0010 |
| 2026-10-15 | **尽快做成「相对成熟、可以分享给朋友用」的产品** | 成熟度扫查按「新朋友第一次用」的视角做；瘦身并行推进 |
| 2026-10-13 起，2026-10-16 重申 | **体验持续向 Hark 看齐** | 一个长期循环：测试 → 找出与 Hark 的差距 → 修 → 上线 → 再测；细节由维护者判断。范围：AI 输出内容、思考 / 加载的呈现、自定义面板、内置电脑控制、机器人自己的对话方式 |
| 2026-10-14 | **把 Hark 的功能都给 ChisaBot** | 记忆、技能、保险箱、GitHub、页面、定时任务、文件 / 生图、审批……逐项补齐；「Google 账号不急」——Google 账号连接放最后（CB-013） |
| 2026-10-15 | **多用户以后再做：隐藏，不删除** | 一度删除朋友账号（#130），同日更正为「隐藏」：代码、签名身份、按人隔离继续保留且必须继续可用；入口和邀请默认关（`CHISABOT_ACCOUNTS_UI`、网关 `invites`）。→ ADR-0011 |
| 2026-10-16 | **发布新版前审查全部功能：没必要的隐藏或删除** | 可恢复的隐藏优先（`CHISABOT_EXTRAS`）；明显的死代码删除；有争议的交给所有者决定（[features.md](features.md) §「待决定」） |
| 2026-10-12 | **仓库公开，任何人都能部署** | 仓库里不能有密钥、私人主机信息、个人信息；私有运维资料只存在仓库之外 |

## 2. 发布与流程

| 日期 | 原则 | 说明 |
|---|---|---|
| 2026-10-12 | **每个改动都走 GitHub PR，再合并** | 不直接推 main；PR 描述写 `Backlog: CB-0xx` |
| 2026-10-13 15:13 | **「做好一版就发」** | 一个 ChisaBot 版本完成并验证后，直接合并、部署、发版，不再逐项等确认。取代 2026-10-13 09:10 的「每个功能点确认后再提交推送」和 2026-10-12 的「网页先给所有者看，确认后再同步桌面 / 安卓」。→ ADR-0008 |
| 2026-10-14（15:27 事故之后） | **绝不强推 main** | 合并前 rebase；`--force-with-lease` 只用在自己的分支上 |
| 2026-10-14 21:20 | **并发推进** | 多个 worker 各用自己的 worktree / 分支 / 预览容器 / 端口；部署一律串行（`deploy-serial.sh`）；worker 不能删上游功能（由瘦身分支统一决定）。→ [dev/parallel-work.md](dev/parallel-work.md) |
| 2026-10-14 22:16 | **瘦身顺序：先入口、后代码、最后数据** | 「按你的建议来」；2026-10-15 拆为前端瘦身（P1、P4a）与后端瘦身（P2 / P3 / P4b）两条线；DROP 表（P5）要在 P4 稳定 ≥ 2 周后。→ [slimming.md](slimming.md) |
| 2026-10-15 | **要有良好的项目维护系统和文档系统** | 需求多且杂：ROADMAP / BACKLOG / ADR / 文档索引 / 版本记录要跟上每次上线 |
| 2026-10-15 / 10-16 | **进度要及时同步，需求面板保持最新** | 每个条目开始或上线都更新看板（ROADMAP「最近完成」、BACKLOG 状态） |

## 3. 测试与生产安全

| 日期 | 原则 | 说明 |
|---|---|---|
| 2026-10-12 | **自测绝不写进真实对话** | 用管理员自检 `POST /api/admin/smoke`（模型往返一次，什么都不保存） |
| 2026-10-13 起 | **生产测试只用一次性机器人 + 临时会话，跑完清理** | 绝不改动、删除所有者自己的机器人和对话；删除只走带快照的守卫脚本；上线前后对比生产快照 |
| 2026-10-16 起（惯例） | **生产上默认只读检查** | 生产 e2e 拦截所有非 GET 请求；需要写的场景放在预览容器（生产数据副本、出网封锁）里跑 |

## 5. 界面与交互

| 日期 | 原则 | 说明 |
|---|---|---|
| 2026-10-10 | **整体要更丝滑、更流畅** | 反馈分层：按钮内状态 → 局部骨架 → 只有大操作才全页加载；动效 150–300ms；不跳、不白屏。→ DESIGN §1–§3 |
| 2026-10-10 | **聊天左栏只列机器人，没有对话列表** | 主机器人置顶；历史对话在机器人 ⋯ 菜单里。→ ADR-0001（2026-10-15 曾被 ADR-0014 修订；ADR-0014 已于 2026-10-26 作废，CB-099） |
| 2026-10-11 | **原型必须能点** | 截图墙不是原型；要在隔离沙箱里给可交互原型。重新布局要真的重排，不只是删图标 |
| 2026-10-11 | **生成式界面只用 json-render 的 render_ui** | Open Generative UI（沙箱 HTML）关闭 |
| 2026-10-11 | **右上角只有窗口按钮**；没有首页 / 新聊天，打开就是机器人聊天 | DESIGN §19–§21 |
| 2026-10-12 22:06 | **「中间不要白板，整个应用一个颜色」** | 聊天中间列没有底板。→ DESIGN §24 |
| 2026-10-12 | **要有设备列表：列出所有已关联的设备，任何一个机器人都能管理** | 设备属于账号。→ ADR-0002 |
| 2026-10-12 21:34 | **设置「大幅度精简」** | 21:09 隐藏管理后台「游乐场」和「谁可以进入」整组 |
| 2026-10-13 | **品牌：所有者选定的动漫头像是 logo 和主题核心** | 发带红 / 海蓝只用在品牌位置，界面强调色保持蓝色；字标 Sora「Chisa」品牌红 +「Bot」墨色（所有者否掉了 Fredoka 黑边版，交给设计者自定）。→ DESIGN §28 |
| 2026-10-13 09:22 | **面板要给机器人设计规范和工作流程，而不是手工修某个面板** | → DESIGN §29、§77 |
| 2026-10-13 15:05 | **机器人浏览器不使用无头模式** | 默认在 Xvfb 里有界面运行（无头会被 Cloudflare 拦）。→ DESIGN / `COMPUTER_BROWSER_MODE` |
| 2026-10-14 17:07 | **链接卡像 Hark；机器人资料页「要简洁高效」** | → DESIGN §47、§48 |
| 2026-10-16 | **右栏「计算机」外面不需要标签** | 标签只在放大的浏览器里。→ DESIGN §96 |
| 2026-10-16 | **5 分钟内连续输入不翻页上跳** | 超过 5 分钟按原来的对齐到顶。→ DESIGN §94 |
| 2026-10-16 | **PC 登录窗无边框、圆角；弹窗不要多一圈边框** | → DESIGN §91 |
| 2026-10-16 | **每个机器人要保留各自的操作状态** | 面板 / 计算机、草稿、滚动位置按机器人 / 对话记住。→ DESIGN §88 |
