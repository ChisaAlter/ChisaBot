## 独立产物核验与修正历史

最终真实下载文件在本机重新打开和执行，没有手工修改文件冒充机器人交付：

- 两份工作簿可读、说明表与差额/总计公式保留。LibreOffice 在独立副本重算全部 15 个公式，结果为初版 24,000 / 25,100 / +1,100，新版 26,000 / 26,200 / +200。这证明公式正确，不代表线上原始附件已重新写入公式缓存。
- 最终 Word 与明细一致：设计/测试/运营/培训分别节余 800/200/100/200，共 1,300；抵减研发超支后净超预算 200。已实际渲染并阅读一页，标题、表格、三条结论和两条行动完整，无截断。LibreOffice 提示缺 Courier，不影响本次所见内容；不保证与所有原生 Office 排版完全相同。
- 最终下载的 CLI、测试和 CSV 保持可直接运行的原文件名。最新版 5 项 unittest 通过；此前版本为 6 项，不能沿用旧计数。
- 独立 Windows 子进程关闭 UTF-8 模式并移除继承的 I/O 编码，BOM、筛选、非法金额、空表四项通过。另强制 `PYTHONIOENCODING=cp936`，对实际下载脚本捕获原始字节：中文正常 stdout 和中文错误 stderr 均能严格 UTF-8 解码。该证据独立于生成测试自身配置 UTF-8 的行为。

保留了失败与纠正过程：

1. PR #283 首轮控制流程通过，但环境缺 openpyxl，模型手工拼文档；Excel 明细/公式正确，却把 24,800 / -1,200 写进 Word 和总结。下载 CLI 在 Windows 默认编码下也失败。PR #284 补齐依赖与具体核验指导。
2. PR #284 后一轮在显式单条发送处失败：模型把原文“等我主动发送”理解为仍需等待，没有执行。PR #285 明确这次点击的含义，最终真实模型验证一个调用通过。
3. 最终轮首次 Word 中“设计、测试、培训合计节余 1,200”是正确的三类小计，旧验收脚本无条件排斥 1,200 属于误判。独立语义复核另发现真实缺陷“运营超预算 -100”，把节余叫成超预算。一次反馈后机器人修正实际文件、重新分享；最终语义校验与视觉检查通过。已修正验收脚本，未将该三类小计报道为算错。
